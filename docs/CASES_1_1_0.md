# УИИ 1.1.0 — отдельные формы дел и изображения

## 1. Изменённые файлы

- `app/ext/uii/portal/controller/dashboard.php`: обработка форм, переходов состояний, вложений и истории.
- `service/case_schema.php`: независимые наборы полей и изображений каждого типа; `service/case_submissions.php`: защита создания от повторной отправки; `service/evidence.php`: проверка и сохранение файлов; `service/case_status.php`, `domain/workflow.php`: достоверные статусы.
- `migrations/v015.php`: новая служебная таблица ключей отправки и лимиты вложений.
- `styles/all/template/form_complaint.html`, `form_request.html`, `form_inspection.html`: отдельные формы. Общие `form_start.html`, `form_end.html`, `field_control.html`, `file_field.html` содержат только повторяемые элементы. `form.html` больше не является универсальной формой.
- Шаблоны `case.html`, `cases.html`, `tasks.html`, `settings.html`, домашняя страница темы и `event/listener.php`: карточки, ссылки, правила и отображение состояний.
- `app/styles/uii_modern/theme/case-form.js`, `portal.js`, `portal.css`: выбор, перетаскивание, предпросмотр, очистка файлов и адаптивность. Метаданные расширения и темы обновлены до 1.1.0.
- `Dockerfile`, `deployment/php/uii-uploads.ini`, `deployment/apache/uii-uploads.conf`: ограничения загрузки. `scripts/apply-portal.sh`: команды PHP выполняются от `www-data`, чтобы не создавать недоступный приложению кеш.
- Новые проверки: `tests/cases_v2.py`, `cases_v2_ui.cjs`, `case_contracts.php`, `scripts/prepare-cases-test.py`, `scripts/test-cases.sh`; обновлены тесты вложений. Документация и сборка установочного пакета дополнены.

## 2. Удалённые и переименованные поля

«Основание» исключено из всех форм, валидации, карточек и отображения истории. В служебном запросе убрано доказательство публикации. В проверке состава убран проверяемый сотрудник. В жалобе убран текстовый протокол опроса.

«Ссылка на дополнительные материалы» проверки заменена загрузкой «Протокол проверки». Доказательство жалобы стало «Фото протокола жалобы», завершающее фото — «Фото ДО». Причина завершения без ответа называется «Если ответ не поступил».

Исторические значения удалённых полей остаются в JSON базы, редактирование их не стирает. Старые URL изображений продолжают открываться ссылками. Старый текстовый протокол не выводится, но сохраняется и учитывается существующим механизмом завершения старой жалобы.

## 3. Отдельные шаблоны и порядок работы

### Служебный запрос

1. Создать: название, адресат, запрашиваемые материалы, комментарий; выбрать скриншот запроса и доказательство уведомления. Можно сохранить черновик без файлов.
2. При редактировании прикрепить недостающие изображения и подтвердить начало срока 48 часов. Публикация больше не требуется. Новые сроки всегда отсчитываются от подтверждения уведомления; прежние даты не пересчитываются.
3. После получения ответа открыть редактирование, заполнить «Ссылка на ответ» и нажать «Завершить запрос». При создании этого поля нет. Сервер фиксирует время регистрации ответа при завершении; дату задним числом пользователь не задаёт.
4. Если ответ не поступил, руководитель после истечения подтверждённого срока заполняет одноимённое поле и завершает запрос. Обычный сотрудник так закрыть дело не может.

### Проверка состава

Создание содержит тип и время проверки, описание, комментарий, три поля изображений. Единственное действие — «Зарегистрировать проверку». После регистрации можно дополнить материалы, начать проверку при наличии скриншота начала, затем заполнить результат и нарушения, прикрепить скриншот окончания и завершить. Протокол проверки остаётся дополнительным материалом, как и прежняя ссылка на дополнительные материалы. Незавершённые внутренние состояния работают без декоративных плашек. Завершение и отмена остаются видимыми.

### Жалоба

Создание: заявитель, фигурант, описание, комментарий и фото протокола жалобы. При редактировании доступны завершающие материалы: «Фото ДО», результат, нарушения и наказание. Завершает жалобу руководитель после заполнения необходимых материалов.

Ответственный нового дела всегда автор из серверной сессии. Поля назначения нет; подставленный клиентом идентификатор игнорируется. У старых дел сохранён прежний `assigned_id` и связанные права доступа, но в интерфейсе ответственным указан автор.

### Независимая настройка форм разработчиком

В `service/case_schema.php::fields()` для каждого типа отдельно задаются подпись, способ ввода (`text`, `textarea`, `url`, `choice`) и обязательность. Эти определения используются и серверной валидацией, и общим элементом `field_control.html`. Размещение и состав видимых полей задаёт соответствующий `form_<тип>.html`, а не общий цикл по полям всех типов. Наборы и названия изображений находятся в `slots()`/`uploadSlots()`. Изменение этапов проверяется в `caseTransition()`. Динамический конструктор форм в ACP не добавлялся.

## 4. Загрузка и хранение

JPG/JPEG, PNG, WebP; до **5 МиБ = 5 242 880 байт** на файл. На запрос достаточно 20 МиБ для трёх изображений и multipart-обвязки. Проверяются ошибка PHP, происхождение HTTP-upload, расширение, реальный MIME через Fileinfo, сигнатура/размеры изображения и совпадение расширения с содержимым. Ограничение 24 Мп и 12 000 пикселей по стороне защищает обработку от чрезмерных размеров.

Предпросмотр работает через локальный Blob URL без передачи файла на фотохостинг. Выбранный до отправки файл можно убрать или заменить. После ошибки сервер просит выбрать новые файлы заново. Уже сохранённые материалы остаются неизменными.

Используется существующая оптимизация GD с ограничением памяти: уменьшение больших изображений, JPEG/WebP 85, PNG без потерь; замена только при уменьшении минимум на 5%. Если обработке не хватает памяти, сохраняется проверенный оригинал. Новых библиотек нет.

Файлы сохраняются со случайным именем `.bin` в `files/uii_evidence` или `UII_EVIDENCE_PATH`. В БД хранится JSON метаданных, содержимое файлов и Base64 туда не попадают. Общая квота остаётся 500 МиБ. При ошибке сохранения нескольких изображений новая партия удаляется, транзакция дела откатывается. Для обычной обработки списков содержимое файлов не читается.

В карточках — подписанные ссылки «Открыть изображение». Контроллер перед каждой выдачей проверяет регистрацию, роль и доступ к делу, устанавливает приватное отсутствие кеширования и `nosniff`. Завершение дела не снимает ограничения доступа. Прямой доступ к каталогу закрыт `.htaccess`; на Nginx запрет нужно повторить в настройках сервера. Невозможно сделать приватными старые внешние URL, если они уже опубликованы на стороннем сервере.

## 5. Исправленные ошибки

- Своевременный ответ больше не показывается у открытого запроса или без подтверждённых данных. Для результата проверяются ссылка на ответ и порядок дат: начало ≤ ответ ≤ закрытие ≤ текущее время; срок должен быть позже начала.
- Повторный/одновременный POST создания с одним ключом возвращает одно дело, одну тему и одну запись истории. Ключ связан с автором и типом; срок действия сутки. Просроченные ключи очищаются при выдаче новых.
- Сохраняется защита редактирования по версии и CSRF. Параллельная устаревшая отправка не перезаписывает чужие изменения, её новые файлы удаляются.
- Убрана возможность назначить другого ответственного через подмену формы.
- Исправлено отображение кнопки очистки пустого поля загрузки: стиль кнопок не переопределяет `hidden`.

## 6. Выполненные проверки

Проверено в отдельной полной установке phpBB 3.3.19 с текущим расширением и SQLite3, PHP 8.5 CLI/GD. База ноутбука и Docker основного устройства не запускались и не изменялись.

- 13 групп HTTP-проверок: три типа дел и их завершение; несколько файлов; прямое открытие ссылок; гости и чужие дела/закрытые вложения; подмена автора/ответственного; старые URL и сохранение исторических данных; CSRF, устаревшая версия; запрос без ответа; параллельная двойная отправка.
- Ровно 5 МиБ принимаются; 5 МиБ + 1 байт отклоняется. Исполняемые файлы, SVG, поддельные изображения и несовпадение расширения/содержимого отклоняются. Ошибка второго файла откатывает всю новую партию.
- Браузер Chromium: девять сочетаний формы/ширины (360, 768, 1440), предпросмотр, удаление, замена, перетаскивание, ограничение размера, настоящая multipart-регистрация проверки, отсутствие встроенных сохранённых изображений.
- 34 проверки контрактов полей, этапов, дат, статусов и конфигурации; 44 проверки хранилища/контроллера; отдельный HTTP-тест оптимизации и квоты; тесты JPEG, PNG с прозрачностью, WebP, EXIF и нехватки памяти.
- Проверены PHP-синтаксис, 33 шаблона Twig, права, учётные записи, административные проверки, кеширование, локализация и контраст обеих тем.
- Новый установочный архив проверен отдельной чистой установкой: v015 и лимиты применены; русский установщик открыт в Chromium в обеих темах на 360/768/1440 пикселях.

Команды воспроизведения и ограничения приведены в `docs/TESTING.md` и `scripts/test-cases.sh`. Старые сценарии предыдущих версий, ожидающие универсальную форму, URL вместо файлов и переключение начала срока на публикацию, сохранены отдельно за флагом UII_LEGACY_TESTS=1 и не являются приёмочными тестами 1.1.0.

## 7. Ограничения и нерешённые проверки

Не выполнены обновление и браузерная проверка непосредственно на Debian-ноутбуке: SSH без интерактивного пароля недоступен. MariaDB 10.11/PHP 8.3 Docker в этом запуске не проверены; интеграционные результаты выше относятся к изолированному SQLite/PHP 8.5. Перед открытием обновления другу нужно выполнить миграцию на ноутбуке и кратко повторить три сценария с его реальными правами.

Результат «ответ вовремя» оценивает время регистрации полученного ответа в УИИ. Внешний сайт не предоставляет системе подтверждённую дату публикации ответа.

## 8. Миграция и конфигурация

Миграция **v015 обязательна**: добавляет `uii_case_submissions`, меняет лимит стандартных вложений phpBB и групп изображений на 5 МиБ, фиксирует настройку начала новых сроков по уведомлению. Существующие дела/файлы не удаляются и не переписываются. Старые даты сохраняются. До миграции новые формы возвращают понятное сообщение о необходимости обновления.

Docker: пересобрать `web`, затем запускать `php bin/phpbbcli.php db:migrate` и `cache:purge` **от `www-data`**. Сохраняйте текущий `compose.yaml` ноутбука с его привязкой портов; пакет обновления его не содержит.

Обычный PHP-хостинг: PHP 8.1–8.3 (расширение УИИ требует PHP не ниже 8.1), Fileinfo; GD с JPEG/PNG/WebP для оптимизации. Задать `upload_max_filesize=5M`, `post_max_size=20M`, `max_file_uploads=3` через панель хостинга или `.user.ini` (если поддерживается). При запрете этих настроек обратиться к хостеру. Для Nginx установить `client_max_body_size 20m` в нужном location и запретить HTTP-доступ к `files/uii_evidence`; Apache-конфигурация пакета ограничивает соответствующие маршруты 20 МиБ. `LimitRequestBody` нельзя записывать в PHP ini. Проверить наличие свободного места и права записи PHP-пользователя в каталог хранения. Миграция запускается через CLI phpBB либо штатное обновление расширения в ACP после резервной копии.

### Обновление работающего ноутбука

Пакет `uii-cases-1.1.0.tar.gz` содержит только исходники расширения, тему, Dockerfile, deployment, scripts и документацию. В нём нет `.env`, `app/config.php`, `compose.yaml`, БД, файлов пользователей и кеша. Нельзя заменять установленный сайт архивом чистой установки.

На ноутбуке в `~/uii-demo`, до распаковки обновления:

```bash
cd ~/uii-demo
backup_dir=$(mktemp -d "$HOME/uii-before-1.1.0.XXXXXX")
chmod 700 "$backup_dir"
sudo docker compose stop web
sudo docker compose exec -T db sh -c '
    export MYSQL_PWD="$MARIADB_ROOT_PASSWORD"
    exec mariadb-dump --single-transaction --user=root "$MARIADB_DATABASE"
' > "$backup_dir/database.sql"
chmod 600 "$backup_dir/database.sql"
sudo tar -czf "$backup_dir/code.tar.gz" app/ext/uii/portal app/styles/uii_modern Dockerfile deployment scripts docs README.md
printf 'Резервная копия: %s\n' "$backup_dir"
```

При ошибке остановиться, сохранить вывод; до изменения файлов сайт можно вернуть командой `sudo docker compose start web`. Затем проверить SHA256 полученного архива и распаковать его в `~/uii-demo`:

```bash
sudo tar --no-same-owner -xzf ~/uii-cases-1.1.0.tar.gz -C ~/uii-demo
sudo docker compose build web
sudo docker compose up -d web
sudo docker compose exec -T --user www-data web php bin/phpbbcli.php db:migrate
sudo docker compose exec -T --user www-data web php bin/phpbbcli.php cache:purge
```

Выполнять команды по очереди, при ошибке не продолжать. После обновления открыть прежний адрес `http://192.168.1.6:8088/`, обновить страницу с Ctrl+F5. Друг по Tailscale использует `http://100.99.218.9:8088/`. Если приложение сообщает о недоступном каталоге кеша/файлов, исправлять владельца только этих записываемых каталогов, не назначать всему сайту права 777.

### Откат

Остановить `web`. Для отката исходников распаковать `code.tar.gz` резервной копии поверх проекта, пересобрать прежний `web`, запустить и очистить кеш от `www-data`. Добавочная таблица v015 может остаться: старая версия её не использует. Если после обновления уже созданы новые дела, старый интерфейс не сможет полноценно работать с их новыми полями; предпочтительнее исправление вперёд. Полное восстановление `database.sql` допустимо только с пониманием, что оно отменит все изменения пользователей после резервной копии. Файлы пользователей не удалять: сначала сохранить актуальную БД и каталог файлов отдельно.
