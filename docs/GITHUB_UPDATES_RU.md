# УИИ 1.3.0 — обновления из GitHub

## Репозиторий

- Имя: **uii-forum**.
- Адрес: **https://github.com/anrhangels/uii-forum**.
- Описание: **УИИ — закрытый портал на базе phpBB: дела, служебные запросы, проверки состава и баг-репорты.**
- Основная ветка: **main**.
- Лицензия: **GNU GPL v2**, файл LICENSE включён.
- Темы GitHub по желанию: `php`, `phpbb`, `task-management`, `bug-reports`.

Сейчас репозиторий публичный. Это допустимо для исходного кода; данные пользователей в него не включаются. Можно переключить репозиторий в Private — тогда серверу потребуется отдельный fine-grained token с доступом только к этому репозиторию и разрешением Contents: read. Токен вводится только в административной панели по HTTPS, не в чате и не в исходниках.

GitHub хранит собственное расширение, тему, перевод, инструкции и инструменты. Ядро phpBB, vendor, config.php, .env, пользовательские файлы, SQL-копии, runtime, внутренние справочные материалы reference и приватные папки исключены. Поэтому автоматически создаваемый GitHub архив Source code не является полной установкой форума или установочным пакетом обновления.

## Как выпускается обновление

1. Внести и проверить изменения локально.
2. Изменить версию в `app/ext/uii/portal/composer.json`; обновить версии темы и статических ресурсов при их изменении.
3. Если нужна БД — добавить новую миграцию. Не редактировать применённые миграции и не заменять рабочую базу свежим дампом.
4. Зафиксировать изменения, отправить ветку `main`, создать и отправить тег, например `v1.3.1`.
5. GitHub Actions выполнит `.github/workflows/release.yml`, соберёт и проверит **uii-web-update.zip**, затем прикрепит его и SHA256 к новому Release.
6. Администратор сайта проверит новую версию и установит её из панели.

В автоматическую публикацию передаётся только стандартный GITHUB_TOKEN текущего запуска Actions с правом Contents: write. FTP-пароль, токен хостинга и доступ к БД GitHub не нужны. Workflow настроен на теги `v*`; тег должен совпадать с версией composer.json. Релизы предварительных версий и Draft не предлагаются сайту.

Первая версия `v1.3.0` устанавливает сам механизм. Если сайт уже обновлён до 1.3.0, она будет показана как текущая, без предложения повторной установки. Следующее изменение выпускается как 1.3.1 или выше. Установщик не понижает версии.

## Первое заполнение репозитория

На основном компьютере, в каталоге проекта:

```bash
cd /home/anrhangels/uii-forum
git init -b main
git remote add origin https://github.com/anrhangels/uii-forum.git
git add .
git status --short
```

Перед первым коммитом проверить список: в нём не должно быть `.env`, `app/config.php`, `runtime`, `uii-private`, SQL-копий и вложений. Локальный Git уже инициализирован и origin настроен на ваш репозиторий. Если Git уже инициализирован, повторные init/remote add не нужны; адрес проверяется `git remote -v`.

Затем:

```bash
git commit -m "UII 1.3.0: GitHub updates with data preservation"
git push -u origin main
git tag v1.3.0
git push origin v1.3.0
```

Git может попросить настроить имя/почту автора и авторизацию GitHub. Для коммитов можно использовать адрес GitHub noreply из настроек профиля, чтобы не публиковать личную почту. Для HTTPS применяется авторизация GitHub CLI/менеджер учётных данных или токен с правами записи кода и workflow; обычный пароль аккаунта не подходит. Не помещать токен в URL remote, файлы проекта или чат. Публикацию исходников и первый Release пользователь выполняет после проверки подготовленного кода; агент автоматически ничего не публиковал.

Для подготовленного в этой сессии проекта локальные коммит 1.3.0 и тег v1.3.0 уже созданы; остаётся выполнить `git push -u origin main` и `git push origin v1.3.0` с вашей авторизацией GitHub. Личная почта не используется: автор коммита настроен локально через GitHub noreply.

Проверить во вкладке Actions успешное выполнение «Выпуск обновления УИИ» и наличие `uii-web-update.zip` в Releases. Пока Release не опубликован, панель сайта показывает понятное сообщение, а не пытается устанавливать Source code ZIP.

## Административная панель

Пункт **«Управление → Обновления»**, адрес `/app.php/uii/admin/updates`.

Нужны два действующих административных разрешения phpBB:

- `a_uii_updates` — «Может устанавливать обновления кода УИИ из GitHub»;
- `a_extensions` — штатное право управления расширениями.

Основатель получает их по стандартной модели phpBB. Другим администраторам права выдаются в штатной панели форума: Права доступа → Администраторы → Расширенные права. Руководящая должность сама по себе установку кода не разрешает. Перед входом в раздел выполняется повторная проверка пароля phpBB; отдельной системы авторизации нет.

Порядок действий:

1. Сохранить источник `anrhangels/uii-forum`. Для публичного репозитория поле токена пустое.
2. **«Проверить обновления на GitHub»** — увидеть версию и текст Release.
3. **«Загрузить и проверить обновление»** — скачать пакет в приватный каталог; проверить SHA-256 из GitHub API, манифест, версии, список и хеш каждого файла. Код и БД пока не меняются.
4. Подтвердить резервное копирование и нажать **«Создать копию и установить файлы»**. Сайт временно отвечает 503 для остальных действий; вход и панель восстановления остаются доступны.
5. После нового запроса нажать **«Продолжить миграции»**. Короткие шаги ограничены по времени; при необходимости продолжить ещё раз. После завершения сайт автоматически открывается.
6. Проверить работу и скачать резервную копию БД, если нужно сохранить её отдельно.

Все изменяющие действия защищены CSRF. Параллельные обновления блокируются файловым lock. Обычные пользователи не получают доступ к панели, установке, токену или SQL-копии даже через прямой URL.

## Что сохраняется

Пакет разрешает замену только:

- `ext/uii/portal/` — собственный код расширения, без тестов;
- `styles/uii_modern/` — тема;
- `language/ru/` — перевод.

В него не допускаются config.php, .env, каталоги files/store/cache, ядро phpBB, vendor, SQL-дампы, база, пользовательские изображения, символьные ссылки и обходы путей. ZIP извлекается по разрешённому списку вручную, без слепого extractTo. Ничего из пользовательских таблиц не импортируется и не очищается. Файлы вложений не переносятся в новый каталог и не заменяются пустыми.

Перед заменой кода сохраняются оригиналы затрагиваемых файлов и потоковый SQL-снимок таблиц текущего форума. Поддержаны MySQL/MariaDB с InnoDB и SQLite3. Таблицы пользователей, дел, истории и баг-репортов остаются в той же базе с прежними идентификаторами. При создании SQL-копии не используется exec, mysqldump, Docker, SSH или root.

Для автоматических миграций разрешены только добавления таблиц/столбцов/индексов и ограниченный набор декларативных операций phpBB: добавление конфигурации, обновление параметров `uii_`, добавление/назначение разрешений, добавление модулей. Удаление таблиц/столбцов, произвольные custom-обработчики и системные изменения блокируются до старта миграции. Для таких выпусков потребуется ручная проверка и штатное выполнение миграций после неё.

Обновление не переустанавливает phpBB и не удаляет аккаунты. Однако оно исполняет код владельца выбранного репозитория: защита GitHub-аккаунта и проверка выпуска остаются обязательными. SHA-256 проверяет целостность скачанного asset и не является независимой подписью издателя.

## Приватное хранение и требования хостинга

По умолчанию папка: `uii-private/updates` рядом с публичным корнем. Если уже настроен внешний `UII_EVIDENCE_PATH`, используется `updates` рядом с его каталогом. При необходимости в config.php можно заранее определить абсолютный `UII_UPDATES_PATH` вне публичного корня. Внутри web root установщик хранить токен и копии не разрешает.

Каталог создаётся с режимом 700, JSON-настройки и SQL-копии — 600. В нём находятся токен, состояние, ZIP, распакованный код и резервные копии. Он должен быть разрешён open_basedir и доступен PHP на запись. В публичный репозиторий этот каталог не отправляется.

Нужны:

- PHP ≥8.1; для SpaceWeb предпочтительна 8.3, PHP 8.2 также соответствует требованиям кода;
- ZipArchive;
- исходящий HTTPS к `api.github.com` и GitHub CDN, OpenSSL/корректные CA; используется уже имеющийся Guzzle, cURL необязателен при доступном PHP HTTPS stream;
- запись PHP в разрешённые каталоги кода и приватный каталог, rename, flock;
- достаточное место для БД, ZIP, stage и прежних файлов.

Проверка версий выполняется только по кнопке администратора. Cron, постоянный опрос, Node.js, Git и SSH на хостинге не нужны. Для приватного репозитория токен можно ввести только через HTTPS; в HTML он повторно не выводится и в БД не сохраняется. При HTTP-доступе публичный репозиторий работает без токена.

Ограничения пакета: ZIP до 16 МиБ, содержимое до 64 МиБ, один файл до 8 МиБ, до 4096 записей. SQL-снимок до 256 МиБ. Перед установкой оценивается свободное место; disk_free_space не показывает точную персональную квоту аккаунта, поэтому любая ошибка записи останавливает установку. Старые копии не удаляются автоматически: после проверки храните их вне хостинга и очищайте старые приватные job-папки вручную. Нельзя удалять текущую job-папку во время установки.

Изменение Dockerfile/Apache или ядра phpBB этим веб-пакетом не выполняется. Для таких обновлений нужен отдельный административный перенос. Старые исходники, отсутствующие в новом пакете, автоматически не удаляются.

## Первоначальная установка механизма на уже работающий сайт

Сам механизм сначала требуется установить обычным способом — пакет 1.3.0 и миграция **v017**. Пользователей и дела повторно не импортировать и phpBB не переустанавливать.

### Ноутбук с Docker

1. Передать `release/uii-update-1.3.0/uii-update-1.3.0.tar.gz` и SHA256SUMS на ноутбук, как раньше. Проверить SHA256.
2. Остановить web и сохранить текущие БД и код, как при предыдущих обновлениях. Не восстанавливать старую базу поверх текущей.
3. Распаковать пакет в `~/uii-demo`. Существующий compose.yaml и привязки портов сохраняются.
4. Подготовить приватную папку для штатного образа php:8.3-apache (www-data UID/GID 33) и разрешить запись только в управляемый код:

```bash
cd ~/uii-demo
sudo install -d -o 33 -g 33 -m 700 uii-private
sudo chown -R 33:33 app/ext/uii/portal app/styles/uii_modern app/language/ru
```

5. Подключить дополнительный том через поставленный override, не заменяя свои порты:

```bash
sudo docker compose -f compose.yaml -f deployment/compose.updater.yaml up -d web
sudo docker compose -f compose.yaml -f deployment/compose.updater.yaml exec -T --user www-data web php bin/phpbbcli.php db:migrate
sudo docker compose -f compose.yaml -f deployment/compose.updater.yaml exec -T --user www-data web php bin/phpbbcli.php cache:purge
```

Далее при пересоздании web использовать оба файла compose, чтобы приватный том оставался подключённым. Предыдущие вложения продолжают храниться в своём каталоге и не перемещаются. После Ctrl+F5 основателю доступен раздел обновлений.

### Обычный хостинг без SSH

Загрузить код расширения/темы из первоначального пакета с сохранением config.php и файлов пользователей. Создать доступную PHP приватную папку вне public_html. Для применения v017 без CLI использовать штатное обновление расширения в ACP: предварительно закрыть форум на обслуживание, отключить и снова включить УИИ, **не выбирать удаление данных расширения**. Проверить применение миграции и вернуть доступ пользователям. Если хостинг/панель не позволяют безопасно выполнить этот шаг, остановиться и подготовить отдельную процедуру переноса; не выполнять переустановку форума или импорт пустой базы.

После первоначального включения обновления УИИ выполняются из его панели без SSH. Если PHP не имеет права менять файлы, панель сообщит об этом до замены кода; права 777 всему сайту не назначать.

## Восстановление при ошибках

- Ошибка загрузки/проверки ZIP: работающий сайт не менялся. Исправить источник и повторить.
- Прервано резервное копирование: код ещё не заменялся. В панели можно отменить подготовку.
- Файлы установлены, но миграция не запускалась: **«Восстановить прежние файлы»**. Новые файлы из этой операции удаляются, прежние возвращаются. База и вложения не заменяются.
- Миграция уже началась: автоматический возврат старой БД запрещён. Исправить причину и продолжить либо восстановить согласованную копию вручную с учётом новых данных.
- Если администратор вышел во время обслуживания: обычный вход остаётся доступен, затем открыть `/app.php/uii/admin/updates` и повторно подтвердить пароль.
- Если код вообще не запускается: в приватной job-папке есть `backup/` и `database.sql`. Исходники восстанавливаются через файловый менеджер/FTP. Снятие `maintenance.json` допускается только после проверки согласованности кода и БД. SQL-копия предназначена для восстановления в **отдельную пустую базу**, а не автоматической перезаписи текущих пользователей.

Резервная копия обновления не заменяет внешний полный бэкап хостинга: изображения не копируются, поскольку обновление их не изменяет. Для аварии диска нужен отдельный полный бэкап БД и вложений.

## Что реализовано и проверено

Основные изменения: `controller/updates.php`, сервисы `github_releases.php`, `update_package.php`, `web_updater.php`, `update_backup.php`, миграция v017, routes/services, ACL, навигация и шаблон updates.html, поддержка повторной авторизации в login_body.html. Добавлены сборщик веб-пакета, GitHub Actions, Docker override и тесты. Правила исключения Git расширены, включён LICENSE.

Проверено в отдельной копии phpBB/SQLite, без символьных ссылок на исходники и без рабочей базы:

- загрузка, проверка пакета и замена кода синтетического GitHub Release;
- SQL-снимок восстановлен в пустую SQLite-базу, число пользователей совпадает;
- пользователи, дела, история, баг-репорты, изображение и config.php сохранены;
- откат кода до миграции и сохранение данных;
- добавочная миграция применена; тестовая миграция удаления users заблокирована до старта;
- 27 проверок безопасности: ограничения путей, ZIP traversal/ссылки/дубли/SQL, хеши, версия и репозиторий, HTTPS, отсутствие передачи токена на CDN и его скрытие в ошибках;
- браузер: пароль администратора, CSRF, скрытый токен, требование HTTPS, семь запрещённых обычному пользователю POST-действий, закрытая SQL-копия, обслуживание и вход для восстановления, обе темы на 360/768/1440;
- выполнен read-only запрос к настроенному GitHub, публикации/изменений репозитория не выполнялось;
- базовые тесты проекта, синтаксис шаблонов и проверки прав проходят.

Реальные скачивание опубликованного Release и полный цикл на SpaceWeb/MySQL пока не проверены: репозиторий ещё пустой, доступа к целевому аккаунту нет. На SpaceWeb нужно проверить исходящий HTTPS, ZipArchive, InnoDB, персональную квоту и права записи. Эти ограничения не скрываются; данные рабочего сайта в тестировании не использовались.
