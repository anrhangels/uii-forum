## Проверки форм 1.1.0

`bash scripts/test-cases.sh` запускает актуальные локальные проверки контрактов, вложений, шаблонов и оптимизации. `UII_CASE_HTTP=1 bash scripts/test-cases.sh` дополнительно запускает HTTP- и браузерные сценарии **только** на отдельной установке `runtime/cases-v2-sandbox` по 127.0.0.1:8094.

Для воспроизведения интеграции: подготовить свежий установочный пакет (`python3 scripts/package-install.py`), передать его каталог через `UII_INSTALL_KIT=/полный/путь python3 scripts/prepare-cases-test.py` либо использовать каталог из `release/LATEST_INSTALL.txt`. Требуются SQLite3 и GD для используемого локального PHP (пути к модулям заданы в скрипте). Скрипт откажется перезаписывать существующую тестовую установку. Применить `db:migrate` к её `site/bin/phpbbcli.php`, запустить PHP со SQLite3/GD, `upload_max_filesize=5M`, `post_max_size=20M`, `max_file_uploads=3`, `PHP_CLI_SERVER_WORKERS=4` и document root `runtime/cases-v2-sandbox/site`. После тестов остановить этот сервер.

Не направлять `cases_v2.py` на рабочий сайт: он специально привязан к отдельной SQLite-базе и меняет даты исключительно собственных QA-дел. Установочные пароли создаются случайно, хранятся в private с ограниченными правами и не входят в релиз.

`scripts/test-all.sh` по умолчанию направляет в актуальный `test-cases.sh`. Старые сценарии версий до 1.1.0 сохранены за флагом `UII_LEGACY_TESTS=1`; они ожидают удалённые поля и прежнюю настройку срока и требуют адаптации перед повторным использованием.

## Практические пределы проверки

Не проводились полноценный аудит безопасности, массовое нагрузочное тестирование, восстановление SQL-дампа в отдельную БД, проверка реального загруженного вложения и всех страниц стандартных ACP/UCP/PM. Запрос вложения в smoke-тесте — только гостевой запрос, он не доказывает всю матрицу прав выдачи файлов.

Одиночный последовательный замер пяти авторизованных страниц дал медиану 5 мс и максимум 6,6 мс на этой машине. Это не прогноз производительности Beget. Снимки интерфейса: `runtime/portal-desktop.png`, `portal-dark.png`, `portal-mobile.png`.

Обновление рабочего интерфейса: `tests/workspace_ui.cjs` проверяет панель управления, поиск сотрудников, добавление, действия в строке и мобильные раскладки. Скриншоты: `runtime/admin-refreshed.png`, `runtime/employees-refreshed.png`. Эти проверки не изменяют данные сотрудников.

Календарь и ACP: `app/ext/uii/portal/tests/activity.php` — 16 проверок; `tests/calendar_acp.cjs` — реальная системная панель после повторного ввода пароля, календарь, мобильный экран, темы, контакты, расположение содержимого и форма настроек. Проверка формы — чтение, без изменения системных параметров. Скриншоты: `runtime/workspace-calendar.png`, `workspace-calendar-mobile.png`, `acp-modern.png`, `acp-modern-dark.png`, `acp-modern-mobile.png`, `acp-settings-modern.png`. Серверная проверка обновлений phpBB возвращает 403 внешнего источника и не считается пройденной.

Дополнительно проверены пустые контактные блоки на простых технических страницах phpBB (окно смайлов). Основные подписи вкладок ACP проверяются без учёта CSS-регистра текста.

Аудит 0.5.0: `tests/roles_matrix.py` создаёт четыре временных аккаунта и проверяет реальные GET/POST-права всех уровней, недопустимые назначения и подмену ответственного.
